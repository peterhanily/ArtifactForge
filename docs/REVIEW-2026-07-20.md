## 🔴 The big one: the real-run "join" is a tautology

- The shipped `tests/test_real_run_join.py` asserts `c.sha256 == sha256(bytes it just wrote)`
  and `amcache == "0000"+c.sha1` (the same expression on both sides). It never compares
  against EvidenceForge's *emitted* hash.
- Proof: for `gpupdate.exe`, EF emits SHA256 `ce7b4d72…`; ArtifactForge's ContentStore makes
  `e42487f7…`. **Not equal.** The join only holds if you *patch* EF's log to your hash — and
  the repo contains no patcher (the library imports `evidenceforge` zero times).
- The genuine "patch a copy of EF's output → all hashes agree" proof exists only as a
  scratchpad spike, not in the repo. Your README ("four-way join … holds on a real run",
  "five-way join") describes the spike, not the shipped code. In `test_cross_emitter_join`
  the "after" join is literally `zeek_field = c.sha256; sysmon_field = c.sha256` — a variable
  assigned to itself.
- **What this means:** the repo, as it ships, proves *identity recovery* (which binary each
  Sysmon hash denotes — and that part is excellent, see below) plus *internal* self-
  consistency. It does **not** yet prove reconciliation with EvidenceForge's logs.
- **Fix (both):** (1) port the spike's patch-and-compare step into the repo so a real EF
  record's hash, after patching, equals the ContentStore hash — a genuine cross-tool
  assertion; (2) correct the README to say "identity recovery on a real run; reconciliation

## Correctness & invariants

| Invariant | Verdict | Evidence |
|---|---|---|
| Determinism (no wall-clock/entropy; byte-identical) | ✅ | 200-scenario batch identical across runs and `PYTHONHASHSEED` 0/1/2 |
| Artifact validity (≥2 independent parsers) | ✅ hives, PE | regipy + python-registry; pefile + lief |
| ContentStore integrity on cache hit | 🔴 | corrupt a `.content-cache` file → `materialize()` returns the correct hash but serves the corrupted bytes to downstream artifacts |
| Answer key not leaked to the agent | ✅ | `Task.public()` omits `expected`; hashes/UUIDs absent from the public view |

**🔴 H1 — ContentStore serves corrupt/stale cache silently.** `materialize()` trusts any file
already at the content-addressed path and never re-verifies it, and the write is non-atomic.
A partial first write, a disk-full, or two parallel batch workers writing the same path
(you advertise "embarrassingly parallel") leaves a torn file that is then trusted forever,
while the returned `Content.sha256` still claims the right value. **Fix:** write to a temp
file + `os.replace()` (atomic); on a cache hit, re-hash and rewrite if it doesn't match.

## Bad data & bad commands (what breaks)

I threw hostile input at every entry point. The crashes are mostly "loud and safe," but three
produce **wrong output with no error**, which is worse for a forensics tool.

**Silent wrong output (fix first):**
- 🟠 **Filename collision drops the PE.** If the malware's filename is `Amcache.hve`,
  `Software.run.hive`, or `JOIN_MANIFEST.json`, that artifact overwrites the PE in the output
  dict. The scene ships with **no PE on disk** but the answer key still asserts its SHA256 —
  an unanswerable task. **Fix:** reserve those names / write the PE to a dedicated key.
- 🟠 **macOS `bundle_id` path traversal.** `bundle_id="../evil"` writes `evil.plist` *outside*
  the scene directory. **Fix:** `os.path.basename()` the plist/xattr filenames.
- 🟡 **Empty `bundle_id`** → `.plist` dotfile, which `Task.public()` hides → the persistence
  question becomes unanswerable.

**Loud crashes on bad input (harden):**
- 🟠 **`grade(None)`** (or any non-dict submission) throws instead of scoring 0.
- 🟠 **`run_count` outside 0…2³²-1** crashes the prefetch writer (`struct.pack`).
- 🟠 **A single malformed Sysmon `Hashes` field** aborts the whole reverse-map over a real EF
  run (`dict(kv.split("="…))` with no `=`, or no `SHA256`). Parse defensively and skip.
- 🟠 **Unicode registry *names*.** The hive writer `.encode("latin-1")`s key/value names;
  a localized/Unicode autostart name (e.g. `Обновление`, `更新`) throws. Value *data* is
  fine (UTF-16). Real registry names can be Unicode — emit UTF-16 names or document ASCII-only.
- 🟡 Empty `out_dir`, trailing-separator `exec_path`, or a 5k-char filename throw OS errors.

**What correctly held up (the robustness floor):** determinism under adversarial hash
ordering; empty/newline/NUL/10k-char `content_id`; hostile usernames (empty, emoji, Cyrillic,
`../../etc`, quotes) — traversal is only reachable via `bundle_id`; Unicode in all *data*
fields; `grade()` with junk-but-dict answers (ints, lists, 5 MB strings, unknown keys);
`generate_batch(0/1/3)`; `run_count` at the 0 and 2³²-1 boundaries.

## The EvidenceForge integration

**✅ Constitution honored.** Augment-not-replace is real: my tree stays clean, you're pure
stdlib with `dependencies = []`, no push/network/subprocess surface, artifacts disclosed inert.

**🔴 It's identity-recovery for Sysmon only — state that plainly.** What the repo actually does
against a real run of mine: recompute my per-emitter seed strings to recover *which logical
binary* each Sysmon hash denotes — and that part is genuinely excellent: **13,748 / 13,748**
hashed records reconstructed, with the EID1 (no-desc) vs EID7 (+desc) formulas both exactly
matching my `sysmon.py`. But it stops there: no Zeek reconciliation on a real run (the
`files.log` is mostly SSL-cert rows using a different seed you don't model), no patcher, and
the cross-emitter join is shown only on a hand-fed dropper dict.

**🔴 The reverse-map has zero CI coverage.** The only test that exercises it is
`skipif(not ARTIFACTFORGE_EF_OUT)`, and CI never sets that variable — so CI is "24 passed,
1 skipped," and the skipped one is the integration. A formula change on my side would sail
through your CI green. **Fix:** generate a tiny EF run in CI (or vendor a fixture) and set the
variable so the reverse-map actually runs.

**🔴 Coupling is fragile and fails silently.** You discriminate EID1 vs EID7 by *EventID*;
I discriminate by *call site* (`rendered_identity` vs `host`). They coincide today by luck.
If I add hashes to a new event type, or change how a field is rendered vs seeded, your
`content_id()` returns a *wrong* identity with no exception — the library has no comparison
against my emitted hash. The one guard (`reverse_ok == with_hashes`) is in the test that
doesn't run in CI. **Fix:** in the library, verify the recomputed hash equals the emitted one
and fail loudly on mismatch; don't route unverified identities through ContentStore.

**🟠 The "small upstream PR" is not small.** Content-first identity is the right long-term
home, and my email-attachment path already hashes real bytes (a precedent). But threading one
identity through my stack means: adding public API (I expose none today), *materializing bytes
for executed PEs* (I never do — only path+metadata exists), rewiring three emitter hash paths
through the dispatcher, and extending `GROUND_TRUTH.json` (which has zero hash labels today).
That's a medium, cross-cutting contribution touching 3+ subsystems, gated off by default —
not a one-field patch. Worth doing; just don't undersell it to me.
